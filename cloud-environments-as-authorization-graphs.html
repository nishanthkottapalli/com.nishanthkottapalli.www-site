Cloud environment as a graph, with authorization attached to interactions.

A network path answers whether traffic can arrive. Authorization answers whether this subject, through this workload, may perform this action on this tenant-owned resource—at the moment the receiving boundary enforces it. Let's see how to model the Cloud as a Graph

Cloud architecture diagrams usually show where traffic can flow. Security decisions require a second graph: who is acting, through which workload, for which tenant, under what delegation, against which resource, with what evidence, and at what enforcement time.

Design rule: attach authorization to the interaction—not to the subnet, cluster, service name or fact that two components can establish a connection.

1. Begin with the time-varying network graph

Represent network reachability at time t as:

GN(t)=(V,EN(t))

The vertex set V contains security-relevant principals and endpoints: clients, gateways, workloads, service proxies, queues, workers, databases and object stores. An edge in EN(t) says that the relevant transport can reach the relevant endpoint at time t.

Edges are typed. “Can reach” should be evaluated for the actual protocol, destination, port, route, service-discovery result and encryption requirements:

e=(wi,wj,κ,endpoint,interval)
Vclients, gateways, workloads and managed-service endpoints
EN(t)network paths available at enforcement time
κtransport and protocol, such as HTTPS, gRPC or a queue API
Nij(t)binary reachability for the relevant edge conditions

The graph changes as workloads scale, endpoints rotate, routes propagate, security groups change and service discovery returns new instances. A diagram captured during design review is therefore not necessarily the graph enforced during a request.

2. Carry a complete request envelope

For a service-to-service request, model the security-relevant information as:

q=(s,d,wc,wr,τ,a,o,γ,e,t)
SymbolMeaningWhat must be verified
sOriginal subject: user or autonomous workloadStable identity, authentication method and current status
dOriginating device, when applicableDevice identity, posture and binding to the session
wcCurrent calling workloadRuntime identity—not merely an IP address or node identity
wrReceiving workloadIntended audience and endpoint identity
τTenant the operation acts forTrusted derivation and binding across every hop
a, oRequested action and resourceCanonical action, resource type and exact identifier
γDelegation or workload authorization credentialIssuer, audience, scope, lifetime and chain restrictions
eVerified contextual evidenceSource, integrity, freshness and relevance
tEnforcement timeDecision and evidence validity at effect time

Do not collapse identities. The original subject s, current workload wc and receiving workload wr answer different questions. Recording only “service A called service B” loses the user, device and delegated purpose behind the call.

3. Keep acting tenant and owning tenant distinct

Let the resource’s owning tenant be:

τo=ownerTenant(o)

For an ordinary tenant-isolated resource, authorization normally requires:

TenantValid(q)≜(τ=τo)∨ExplicitCrossTenantGrant(q)

This prevents two common errors: trusting a tenant ID supplied by the caller without binding it to verified authority, and assuming that reaching a shared service implies access to every tenant partition behind it.

Cross-tenant administration, support access and shared resources are not exceptions to modelling. They are explicit relationships with their own subject, purpose, action, resource set, approval and expiry.

4. An admissible interaction needs both path and permit

Let Nij(t) ∈ {0,1} indicate permitted network connectivity from wi to wj. Let Pj(q,t) ∈ {0,1} be the authorization decision enforced at the receiving boundary.

Aij(q,t)=Nij(t)·Pj(q,t)

Because both terms are binary, multiplication expresses conjunction: the interaction is admissible only when the path exists and the receiving boundary permits the request.

Necessary, not sufficient

Reachability

Nij(t)=1⇏Pj(q,t)=1

A successful TCP/TLS connection does not establish resource permission.

Also necessary

Deliverability

Pj(q,t)=1⇏Nij(t)=1

An abstract permit does not create a route, healthy endpoint or secure transport.

Expand the receiving decision

Pj(q,t)≜SubjectAuthenticated(s,γ,t)∧CallerAuthenticated(wc,t)∧ReceiverIsAudience(wr,γ)∧TenantValid(q)∧ActionAllowed(s,a,o,τ)∧ContextValid(e,q)∧FreshEnough(γ,e,t)

5. Compose authorization across the entire path

Let a request traverse path π = (v0, …, vm). Each hop may receive a transformed request envelope qℓ at time tℓ. End-to-end admissibility is:

Aπ=∏ℓ=1m[Nvℓ−1vℓ(tℓ)·Pvℓ(qℓ,tℓ)]

This formula exposes a crucial implementation fact: passing one gateway does not authorize all downstream effects. The API, queue, worker, database and storage service may enforce different policies over different resources.

Delegation must not amplify authority

If one workload exchanges or attenuates credential γℓ for the next hop, the delegated scope should only stay equal or shrink:

Scope(γℓ+1)⊆Scope(γℓ)∩Need(vℓ+1)

The tenant and original subject must remain bound unless an explicit, separately authorized transition changes them. Forwarding a broad user token unchanged through every internal service is not the only way to preserve identity—and often preserves far more authority than the downstream workload needs.

6. A queue splits one apparent flow into several interactions

For an API that publishes work to a queue and a worker that later consumes it, enqueue, dequeue and data access are separate protected interactions:

Aasync=Aenqueue·Adequeue·Adata

The queue proves that a message was accepted and later delivered according to its own semantics. It does not prove that the producer was allowed to request the business operation, that the consumer is still allowed to perform it, or that the referenced resource still belongs to the same tenant.

The message must carry bounded authority

{
  "message_id": "msg_01…",
  "subject": "user:1842",
  "producer": "spiffe://prod.example/api/orders",
  "consumer_audience": "spiffe://prod.example/worker/orders",
  "tenant_id": "tenant-a",
  "action": "invoice.generate",

  "policy_revision": 417,
  "issued_at": "2026-09-15T10:12:20Z",
  "expires_at": "2026-09-15T10:17:20Z"
}

The consumer authenticates the message source, verifies integrity and audience, rejects replay according to the delivery contract, and reauthorizes the intended effect at consumption time. If the design intentionally preserves the producer-time decision, that is a different consistency contract and must define its maximum lifetime and revocation behaviour.

7. Place PEPs so the protected resource cannot be reached around them

A policy enforcement point can be a gateway, proxy, application guard, queue policy, database authorization layer, object-store policy—or a deliberate combination. What matters is that the enforcement placement forms a cut across every path from untrusted sources to the protected resource.

Let U be the set of untrusted or insufficiently authorized sources, R the protected resources, and CPEP the enforcing vertices or edges. The non-bypass property is:

∀π∈Paths(U,R):π∩CPEP≠∅

A public gateway is not an adequate PEP for a service that can also be reached through an internal load balancer, direct pod address, alternate queue consumer or database endpoint. The graph must include operational, administrative and recovery paths—not only the intended application route.

Enforce as close to the protected effect as practical. An outer PEP can reject broad classes of traffic early. The receiving workload or data boundary still has the most precise resource, action and tenant context.

8. Authorization is evaluated at an enforcement time

The tuple includes t because identity, grants, tenant ownership, resource state, workload health and policy can change while a request moves through the system.

issuedAt(γ)≤t<expiresAt(γ)
t−observedAt(e)≤Δevidence

Those checks are necessary but not sufficient. The PEP must also define its policy-revision and revocation consistency contract. A valid-looking token can describe authority that has since been revoked; a fresh policy decision can still rely on stale tenant or resource state.

For sensitive effects, bind the permit to the resource generation or version used in the decision:

version(o,t)=decisionResourceVersion(q)

If it changed, re-evaluate rather than applying an old decision to a new object state.

Receiving-boundary decision

def authorize_interaction(request, caller_identity, now):
    resource = resources.load_canonical(request.resource_id)
    owner_tenant = resource.owner_tenant

    assert caller_identity.subject == request.calling_workload
    assert request.receiving_workload == THIS_WORKLOAD
    assert request.tenant_id == owner_tenant or cross_tenant_grant(request)
    assert delegation.valid_for(request.action, resource, now)
    assert evidence.fresh_enough(request.context, now)

    return policy.evaluate(
        subject=request.original_subject,
        caller=caller_identity.subject,
        tenant=request.tenant_id,
        action=request.action,
        resource=resource,
        context=request.context,
    )

Effect receipt

The receiving PEP should emit a decision record even for denies, and the protected component should emit an effect receipt for permits. The correlation chain should reconstruct:

network edge → authenticated caller → request envelope
→ policy decision → protected effect → resulting resource version

10. Worked example: tenant-scoped invoice generation

01

Client to gateway. The gateway authenticates user 1842 and device context, derives tenant A from the verified session and authorizes the invoice request route.

02

Gateway to API. The API authenticates the gateway/workload identity, verifies the delegated subject and independently authorizes invoice.generate for order:7821.

03

API to queue. The queue authorizes the API as a producer. The message binds tenant A, order 7821, the worker audience, policy revision and a short expiry.

04

Queue to worker. The worker authenticates message provenance, checks replay and expiry, then reauthorizes the business action at consumption time.

05

Worker to tenant data. The data PEP resolves τo = tenant A, verifies it matches the acting tenant and restricts the query to the authorized order.

06

Verify. Decision and effect receipts show that each reachable edge was permitted, each receiving boundary enforced, and no resource owned by another tenant was read or modified.

11. Verify the graph and the interaction together

The central property is:

∀q,t:ProtectedInteractionExecuted(q,t)⇒PathReachable(wc,wr,t)∧ValidEnforcedPermitAtReceiver(q,t)∧TenantBindingValid(q)∧EffectWithinScope(q,t)
Graph tests

Reachability

  • Enumerate intended and unintended paths.
  • Test alternate listeners and direct endpoints.
  • Compare desired policy with effective routes.
  • Repeat after scaling and failover.
Authorization tests

Interaction matrix

  • Vary subject, caller, tenant, action and resource.
  • Reject wrong audience and stale evidence.
  • Exercise revocation during multi-hop requests.
  • Prove delegation cannot amplify scope.
Boundary tests

Bypass and effects

  • Attempt to route around each PEP.
  • Inject cross-tenant identifiers.
  • Replay queue messages.
  • Compare receipts with actual data changes.

Trust anchors: identity issuers, workload attestation, tenant and resource registries, policy authorities, keys and trust bundles, clocks, service discovery, receiving PEPs and the audit path. If one is compromised, state explicitly which graph or authorization claims no longer hold.
